# CFB and Satoshi: what the primary sources say

<Callout type="warning" title="Correction, September 2026">
This page replaces an earlier version that collected circumstantial evidence and assigned identity percentages. Those percentages had no calibrated method behind them, and several of the numbers they rested on were wrong. See [Corrections, September 2026](/docs/03-results/35-corrections-september-2026).
</Callout>

The question whether Come-from-Beyond (CFB, who names himself Sergey Ivancheglo, message 1501252729325093025) had a part in creating Bitcoin comes up again and again in the Qubic community. This page does not try to answer it. It collects what can be checked: CFB's own statements with their message IDs, the relevant blocks, and how unusual the often cited patterns really are.

## The blocks

| Block | Mined (UTC) | What is special | Checked |
|---|---|---|---|
| 264 | 13 January 2009, 00:19:40 | Pays 50 BTC to a public key whose address is `1CFBdvaiZgZPTZERqnezAtDQJuGHKoHSzg`. After the leading 1 the address contains no digit | Block header and output recomputed |
| 369 | 13 January 2009, 20:45:35 | The public key contains the hex digits `...1d a1 cf b4 ad...`, which can be read as "da 1 cfb 4 ad" | Block data from a public explorer |

Both blocks belong to the set of early blocks that researchers attribute to a single dominant miner (often called "Patoshi"). That attribution comes from a published analysis of mining patterns and is itself not proof of who the miner was.

## How unusual are these patterns?

We checked all 21,953 public keys of that early mining set against a chance model.

| Pattern | Found | Expected by chance |
|---|---|---|
| Address starts with `1CF` | 17 (block 264 among them) | 16.5 |
| Address starts with `1CFB` | 1 (block 264) | 0.28, so at least one such address turns up in about 1 of 4 random sets of this size |
| Address has no digit after the leading 1 | 72 (block 264 among them) | about 65 (simulated from 2,000,000 random addresses) |
| Hex sequence `1cfb` anywhere in the public key | 44 (blocks 280 and 369 among them) | 42.5 |
| Hex sequence `cfb` anywhere in the public key | 649 | about 686 |

All four counts are about what random keys produce. A pattern like `cfb` can be found in some early key with almost any block number one cares to choose, and anyone can search for it in a few seconds.

Two details speak against a hidden encoding in block 369. The digits `1cfb` do not sit on byte boundaries (the bytes are `a1 cf b4`), and neither the text "1CFB" in ASCII nor a Pascal-style string of length 4 followed by "1CFB" appears in any of the 21,953 keys. Every uncompressed public key starts with the byte `04`.

One point is worth stating fairly: CFB named block 369 before anyone had looked at its key. If the number 369 had been fixed in advance for an unrelated reason, a `1cfb` in exactly that key would be about a 1 in 500 event. Because a search over early keys takes seconds and many numbers can be given a story afterwards, this does not make it evidence.

## What holds from our earlier work on the 1CFB address

Earlier versions of this site went much deeper into the 1CFB address. Several of those results are exact arithmetic and still stand. The address transformations (mirror wallets, XOR with the Genesis address) are documented with their status in [chapter 7](/docs/03-results/07-mirror-wallets-keys).

What still stands:
- The HASH160 of `1CFBdvaiZgZPTZERqnezAtDQJuGHKoHSzg` has a byte sum of 2299 = 121 x 19.
- Its XOR with the Genesis address has a byte sum of 2671.

Both are exact. Numbers like these can be found for almost any address once the divisors are chosen afterwards, so they carry no meaning by themselves.

What did not hold up:
- **The chance of a 1CFB prefix.** Earlier pages gave 1 in 195,112. The exact value for a valid address is about 1 in 77,178, and among 21,953 early keys that makes one such address a roughly one-in-four event.
- **The "XOR 13 + 121 = 0" solution for the matrix value at [45, 92].** A step chosen afterwards turns any value into zero, so it is not a test.
- **The "0x7b family".** It lists 8 addresses with first byte 0x7b and byte sum 2299, where chance predicts about 7.
- **The nonce byte 44.** It fits the Patoshi pattern, but on its own it does not prove who mined the block.

## What would settle it

A message signed with the key of block 264, of block 369, or of any other early key of that mining set. It would take a key holder about a minute. As long as no such signature exists, patterns in addresses and keys cannot decide the question in either direction, and neither can our statistics.
